# Webservice REST : Description et caractéristiques

> **Disponible :** **WINDEV** (Windows, Linux) · **WEBDEV** (Windows, Linux)

## Présentation

Un Webservice REST créé avec WINDEV ou WEBDEV est modifiable grâce à l'éditeur de Webservices REST.
Cet éditeur permet de :

- gérer les points d'entrée : ajout, modification, suppression.
- afficher la description du Webservice REST en cours.
- créer la documentation OpenAPI du Webservice REST en cours.

## Gestion des points d'entrée

L'éditeur de Webservices REST permet de :

- Créer des points d'entrée. Pour plus de détails, consultez [Créer des points d'entrée](1410091004.md).
- Modifier un point d'entrée directement depuis l'éditeur.
- Dupliquer un point d'entrée.
- Supprimer un point d'entée.

### Modifier un point d'entrée
Toutes les caractéristiques d'un point d'entrée peuvent être directement modifiées :

1. Description du point d'entrée.
2. Méthode HTTP utilisée : Méthode HTTP représentant l'action à réaliser (GET, PUT, etc.).
3. Format de la requête : Formatage des données passées lors de l'appel REST.
4. Format de la réponse : Formatage des données récupérées en retour d'un appel REST.
5. Ressource ou partie d'URL du point d'entrée.
6. Procédure associée : Procédure WLangage associée au point d'entrée.
7. Désérialisation automatique : Dans le cas d'une action de type POST, PUT ou PATCH, il est possible de désérialiser automatiquement les données passées en paramètre de la requête dans un paramètre de la procédure associée au point d'entrée.
8. Nouveauté 2025
  Permissions : Permissions (scopes) nécessaires pour accéder à ce point d'entrée.

## Description d'un Webservice REST

La fenêtre de description d'un Webservice REST permet de configurer différents éléments :

- Composantes communes.
- Procédure prologue.
- Nouveauté 2025
  Autorisation.

Pour afficher la fenêtre de description d'un Webservice REST : sous le volet "Webservice REST", dans le groupe "Options", cliquez sur "Description".

### Composantes communes
La ressource du point d'entrée est spécifiée lors de la création du point d'entrée.
La ressource est composée :

- d'éléments statiques.
- d'éléments variables.
- de paramètres communs (optionnels).

Les **éléments statiques** représentent les objets manipulés. Par exemple, "/Clients" pour manipuler des clients.
Dans l'assistant de création de la ressource, un élément statique correspond à une "Composante fixe".

Les **éléments variables** identifient les ressources manipulées (un numéro de client, un numéro de commande, ...). Par exemple "/Clients/{NumCli}" permet d'indiquer le client manipulé via son numéro de client.

- Dans l'assistant de création de l'URL, un élément variable correspond :
  - soit à une composante variable de type paramètre de procédure. Cette composante est récupérée automatiquement dans les paramètres de la procédure WLangage associée.
  - soit à une composante variable de type programmation, récupéré par programmation par la fonction [WebserviceParamètre](1000022786.md).
- Un élément variable est représenté par la syntaxe "{Nom composante variable}".
  Par exemple, "/Clients/10" permet de manipuler les clients ayant l'identifiant 10.
- Il est habituel de passer les éléments variables dans l'URL lors d'un appel à une fonction REST.
- Chaque composante variable de type programmation, dans la ressource (URL) du point d'entrée correspond à un paramètre passé à la procédure WLangage associée au point d'entrée.
- Un élément variable est représenté par un nom lors de la définition de l'adresse du point d'entrée dans l'éditeur. **Dans le cas d'une composante variable de type programmation, ce nom doit être identique au nom du paramètre dans la procédure WLangage associé au point d'entrée**.
  Au moment de l'exécution, la valeur passée dans la ressource (URL) sera récupérée et mise dans la variable. Ce nom est sensible à la casse. Il est donc très important d'utiliser le même nom dans la procédure et dans la ressource (ou inversement) sinon une erreur d'exécution est générée.

Il est possible de combiner plusieurs éléments statiques et plusieurs éléments variables. Par exemple:

- "/Clients/{idClient}/Factures" pour récupérer les factures d'un client identifié par son idClient.
- "/Fournisseurs/{idFour}/Produits/{RefProd}" pour récupérer le produit identifié par "RefProd" du fournisseur identifié par "idFour".

L'onglet "Composantes communes" de la fenêtre de description d'un Webservice REST permet de définir une partie de la ressource identique à tous les points d'entrée. Il n'est donc pas nécessaire de copier cette partie de la ressource systématiquement dans chaque point d'entrée. La modification est réalisée à un seul endroit.

### Procédure Prologue
Une procédure "Prologue" est appelée avant d'exécuter la fonction associée au point d'entrée du Webservice (pour plus de détails, consultez [Procédure Prologue](1000022797.md)). Une procédure de ce type peut permettre par exemple de contrôler un jeton d'authentification (token) lors de l'appel de chaque point d'entrée. La procédure **Prologue** est une procédure sans paramètres. Cette procédure doit renvoyer :

- la valeur **Vrai** pour continuer et exécuter la procédure associée au point d'entrée.
- la valeur **Faux** pour arrêter l'appel et ne PAS exécuter la procédure associée au point d'entrée. Dans ce cas, il est nécessaire d'utiliser la fonction [WebServiceEcritCodeHTTP](1000022785.md) pour indiquer le code erreur de retour (erreur de type 4XX ou 5XX).

### Autorisation
Pour utiliser un Webservice REST sécurisé, il est nécessaire de définir les serveurs de confiance et les permissions.
L'onglet "Autorisation" permet de :

- **Définir les serveurs de confiance**
  Il est tout d'abord nécessaire de saisir les informations concernant les serveurs de confiance, permettant de vérifier l'authentification ou les autorisations des utilisateurs.
  Pour définir le(s) serveur(s) d'authentification (OpenID Connect) ou d'autorisation (OAuth 2.0) :
  - Dans la partie haute de la fenêtre, cliquez sur "+" pour ajouter autant de serveurs que voulu.
  - Saisissez les caractéristiques de chaque serveur :
    - Adresse du serveur,
    - Clé utilisée pour la validation du token **ou** URL d'introspection fournies par le serveur (un seul de ces éléments est nécessaire).
  Clé pour la validation du token (vérification de la signature).
  La clé dépend de la signature utilisée par le serveur :
  - Signatures "HS256"/"HS384"/"HS512" : la clé est la clé secrète (partagée avec le serveur). La clé est généralement une valeur binaire, parfois représentée sous forme d'une chaîne en hexadécimal.
  - Signatures "RS256"/"RS384"/"RS512" : la clé est la clé publique du serveur. La clé est une chaîne. Elle est généralement représentée sous la forme d'un texte multiligne qui commence par ----BEGIN PUBLIC KEY-----
- **Définir les permissions (scope)**
  Dans la partie basse de la fenêtre, il est possible de saisir la liste des permissions pouvant être nécessaires pour exécuter un point d'entrée du Webservice.

## Générer la documentation OpenAPI

Il est possible de générer la documentation OpenAPI du Webservice REST : sous le volet "Webservice REST", dans le groupe "Options", cliquez sur "Documentation OpenAPI..." et sélectionnez l'emplacement où le fichier YAML correspondant doit être généré.
