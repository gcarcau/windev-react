# Session_heartbeat

> **Disponible :** **WINDEV** (Windows, Linux, Java, Code Utilisateur (MCU)) · **WEBDEV** (Windows, Linux, PHP, WEBDEV - Code Navigateur) · **WINDEV Mobile** (Android, Widget Android, iPhone/iPad, Widget IOS, Apple Watch, Mac Catalyst)

## SESSIONS WEBDEV : FERMER LA SESSION QUAND L'UTILISATEUR FERME LE NAVIGATEUR (HEARTBEAT)

En Web, la durée de vie des sessions est un élément crucial dans la gestion des ressources du serveur.
En effet, lorsque les sessions durent longtemps, elles ont tendance à s'accumuler sur le serveur. Or, plus il y a de sessions en mémoire, plus il y a de risque de saturer le serveur.
**Avant la version 26**, dans les sites WEBDEV, pour éviter une saturation du serveur, il était recommandé de paramétrer une durée de vie des sessions très courte (par exemple 1 min 30).
En contre-partie, il était nécessaire de programmer un **Timer** en code navigateur pour maintenir la session "en vie" le temps de la
navigation de l'internaute.
Le timer devait effectuer un appel ajax au serveur régulièrement, par exemple toutes les 30 secondes, pour signaler la nécessité
de maintenir la session.
Avec cette solution :

- la session est maintenue tant que la ou les pages du site déclenchent le timer,
- lorsque le navigateur est fermé ou une page d'un autre site affichée, il se passe au maximum 1 minute 30 (paramétrage de la durée de vie de la session) avant que la session ne soit détruite par le serveur WEBDEV.

Depuis la version 26, il existe pourtant une autre **solution méconnue**, automatique et sans programmation pour que :

- la session soit détruite automatiquement lorsque l'internaute quitte le site,
- la durée de vie des sessions puisse être rallongée (et soit ainsi maintenue automatiquement sans programmation de timer).

En effet, depuis la version 26, **WEBDEV propose une gestion optimisée des sessions grâce au "HeartBeat"**.
La fonctionnalité "HeartBeat" ("battement de cœur" en anglais) est un traitement automatique sur le navigateur qui envoie régulièrement (toutes les 5 minutes par exemple) une information au serveur et à la session de l'utilisateur pour indiquer que la page est toujours affichée dans le navigateur de l'internaute.
Lorsque l'internaute ferme la page ou le navigateur, le serveur ne reçoit plus d'information du navigateur et va donc fermer la session **sans attendre le timeout défini pour le site**.
Le HeartBeat du serveur allège grandement la programmation des sites WEBDEV avec session : **les timers et les procédures ajax
de maintien de session peuvent tout simplement être supprimés**.

**Plusieurs points importants :**

- La terminaison anticipée des sessions est effectuée uniquement si le Serveur d'application WEBDEV détecte que la page affichée chez l'internaute est une page du site.
  Ainsi, lors de l'affichage d'une page externe, de paiement par exemple, la terminaison anticipée des sessions n'est pas réalisée.
  Ceci permet au développeur de programmer éventuellement un retour au site marchand après paiement. La session sera en effet encore en vie.

- L'intervalle entre deux battements de cœur du HeartBeat est défini automatiquement par WEBDEV à 5 minutes, par défaut.
  Il est possible de personnaliser cet intervalle avec la fonction WLangage [SessionHeartBeatActive](1000026248.md) :
  ```wlangage
  SessionHeartBeatActive(Vrai, 10 min)
  ```

Le choix de l'intervalle est important.
Si l'intervalle est trop long, le risque est que les sessions restent trop longtemps en vie inutilement.
Si l'intervalle est trop court, le serveur est inutilement chargé par des appels "battements" pour maintenir en vie les sessions.

- Dans le cas des clients mobiles, les appels "battements" consomment des ressources (réseau et batterie).

### Quel est l'impact sur le paramétrage du timeout de session ?
Le timeout de session permet de terminer la session lorsque l'internaute n'a réalisé aucune action sur le site pendant le délai défini.
Si un timeout de session est défini sur un délai trop court (10 minutes par exemple), la session sera fermée au bout de 10 minutes sans action de l'utilisateur même si le navigateur n'est pas fermé.
**Le timeout de session a donc désormais tout intérêt à être défini selon le temps raisonnable qu'un internaute pourrait passer sur le site**.
Prenons le cas d'une application Web par exemple : l'internaute a une page de l'application Web affichée dans son navigateur, en permanence, sur le temps de sa journée de travail.
Grâce au heartbeat, la session sera tuée si le navigateur est fermé.
Pour ce type d'application Web, le timeout pourrait, dans ce cas, être défini raisonnablement sur le temps de travail journalier de l'internaute (7 ou 8 heures, par exemple).
Ainsi, la session sera prolongée tout le long de sa journée de travail, même en cas d'inactivité temporaire (réunion, pause, appel téléphonique, etc).
